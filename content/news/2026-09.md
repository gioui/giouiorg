After another month of community effort, I'm pleased to announce Gio v0.10.3! This release brings support for Input Method Engines (IME) on Linux for both X11 and Wayland. On X11, ibus is specifically supported, whereas on Wayland we now implement the zwp_text_input_v3 interface and will automatically use it on compositors that implement the server side. Effectively, Linux users now can enjoy the same ease of text composition as our other platforms.

Additionally, it is now possible to cancel the close of an application window on desktop platforms (Windows, macOS, and Linux). This feature is unavailable on mobile and WASM. Read below for more details.

# gioui.org@v0.10.3

This month, qiannian polished our windows integration heavily, primarily addressing issues in manipulating the size and position of application windows.

qiannian also contributed the long-awaited feature of window close cancellation. Now when a user requests window close, the window will emit an [`app.ClosingEvent`](https://pkg.go.dev/gioui.org/app#ClosingEvent) on supported platforms (Windows, macOS, Linux). If an application ignores this event, nothing will change and the application window will close. If an application calls the [`Abort()`](https://pkg.go.dev/gioui.org/app#ClosingEvent.Abort) method on this event, the close will be cancelled and the window will remain open.

Alessandro Arzilli contributed support for the ibus IME running under X11, while at the same time bigwolfe implemented support for zwp_text_input_v3 on Wayland.

Many other contributors provided small features or bugfixes this month, check them out below.

# gioui.org/cmd@v0.10.3

Tobias made a number of excellent fixes to the `gogio` CLI that are now available in a tagged release.

## Changes by Author

Tobias Gesellchen:

- **`gogio`**: fix the Windows file version resource layout. VS_FIXEDFILEINFO stores each of the four version components in one 16-bit half of the dwFileVersionMS/dwFileVersionLS pair. buildWindows left the major component unshifted, which moved every component one slot to the right and dropped the version code entirely: -version 0.18.0.0 ended up as 0.0.18.0, and the default -version 1.0.0.1 as 0.1.0.0. [64b6dec](https://git.sr.ht/~eliasnaur/gio-cmd/commit/64b6dec)
- **`gogio`**: set the bundle version in the macOS Info.plist. setInfo put the version into the template data but the template never referenced it, so -version had no effect on a macOS bundle at all: the generated Info.plist carried no CFBundleShortVersionString and no CFBundleVersion. [bfcd8a5](https://git.sr.ht/~eliasnaur/gio-cmd/commit/bfcd8a5)
- **`gogio`**: test that version codes may exceed 16 bits. The fourth version field maps to android:versionCode, which is a plain build counter and routinely larger than the 16 bits a Windows version resource component gets. Pin that down, so the range check added in the next commit is scoped to the platforms that need one, rather than to parseSemver. [a15f862](https://git.sr.ht/~eliasnaur/gio-cmd/commit/a15f862)
- **`gogio`**: reject versions Windows cannot represent. Both the VS_FIXEDFILEINFO fields and the manifest assembly identity give each of the four version components 16 bits. A larger component silently overflowed into its neighbour, so -version 0.0.1.20241024 produced a binary claiming to be 0.0.309.55936 and a manifest Windows refuses to parse. [226ec33](https://git.sr.ht/~eliasnaur/gio-cmd/commit/226ec33)
